# ReactorBench-LM

I built ReactorBench-LM to find out how much a small decoder-only Transformer can learn
when it starts from random weights and trains on a controlled synthetic world. The
model reads event narratives generated by Aster Station, a fictional causal
environment I designed for this project.

> All systems, events, values, policies, and narratives in ReactorBench-LM are
> synthetic and fictional. No real plant records, operating procedures, event reports,
> Navy material, restricted information, or proprietary manuals were used. The model
> is an educational language-model experiment and is not suitable for operational,
> engineering, licensing, emergency, maintenance, security, or safety decisions.

## Current status

I have completed Phases 0–5 and the original Phase 6 experiment locally. Phase 6
produced a verified negative result, which I kept instead of hiding or overwriting it.
I then built a checksum-bound remediation runner so I could improve the model without
quietly changing the data, thresholds, or old results.

The early reruns caught several engineering problems, including MPS device naming, a
counterfactual decoding dead end, inconsistent inventory hashing, and a gate-scoring
policy mismatch. I fixed those issues and kept the failed attempts as reproducible
evidence. The detailed timeline and checksums are in
[the implementation status](docs/IMPLEMENTATION_STATUS.md).

Targeted-03 was the strongest completed candidate so far. It finished all 2,500
training steps and 427 development-gate evaluations, then passed nine of ten checks
after a checksum-bound gate replay. Its only miss was fault-comparator margin:
`-0.0344200` against the required `0.0200000`. No final or golden evaluation was
opened.

Targeted-04 has now run and is preserved as another honest negative result. Its extra
diagnosed-fault sampling overcorrected the class balance: eight of ten checks passed,
fault margin fell to `-0.072348`, and continuation macro-F1 fell to `0.893333`.

The next run is targeted-05. I restored the balanced hierarchical sampler, added extra
loss weight to fault-family and continuation targets, and made checkpoint selection
require task-level development scores rather than relying only on an aggregate score.
The implementation is verified and ready to run, but I have not trained targeted-05
yet. All ten thresholds remain unchanged.

## Research question

Can a small causal Transformer trained entirely from random initialization learn the
temporal structure of a disclosed synthetic event world and generalize to held-out
wording, component roles, and fault combinations better than preregistered simple
baselines?

My goal is to demonstrate the complete path from an invented causal state machine to
a trained and evaluated language model:

```text
latent Aster state
    -> bounded observation channels
    -> canonical events
    -> project-authored narrative renderer
    -> leakage-resistant dataset splits
    -> project-trained tokenizer
    -> baselines and from-scratch Transformer
    -> behavioral, robustness, and compositional evaluation
    -> narrow inference API and Research Editorial interface
```

Ground truth belongs to the structured generator, never to rendered prose or model
output. Developmental generator/dataset contracts are snapshot-reviewed, not frozen as
version 1.

## What I built from scratch

I wrote the project code that defines:

- the fictional causal environment and all scenarios;
- the observation, event, task, grouping, split, and artifact contracts;
- the project-authored renderer and quality/leakage gates;
- the approved tokenizer corpus and tokenizer training configuration;
- token/position embeddings, multi-head causal self-attention, pre-norm residual
  blocks, feed-forward layers, tied output head, shifted targets, and loss;
- random initialization, training loop, deterministic probes, exact parameter counts,
  generation boundary, and safe checkpoint lineage; and
- every test and measured artifact relationship.

PyTorch supplies tensors, automatic differentiation, optimization, and an optional MPS
backend. SentencePiece supplies the BPE trainer. Safetensors supplies a data-only weight
container. These tools do not provide the architecture, weights, corpus, labels, or
model behavior.

## Non-negotiable boundaries

- All scenarios and training narratives are project-authored and synthetic.
- Real plant logs, reports, procedures, manuals, setpoints, facility data, and Navy
  nuclear information are excluded.
- Values are normalized or use explicitly fictional synthetic units.
- The core model receives no pretrained weights and uses no hosted LLM for corpus
  generation, labeling, primary judging, or behavior.
- Outputs are measured fictional labels, not real operating guidance.
- The project is a benchmark and research demonstration, not an operator assistant,
  engineering model, digital twin, safety system, or control-room replica.
- Arbitrary files, URLs, model paths, checkpoints, and real-world logs are outside the
  interface contract.

See [the canonical project requirements](research/PROJECT_REQUIREMENTS.md) for the
complete scope and explicit non-goals.

## Development workflow

- Python 3.12 is the reproducible baseline; Python 3.13 remains in the declared
  compatibility window.
- `uv` manages the locked dependency workflow.
- Pydantic v2 defines strict runtime contracts.
- Model weights are stored as checksum-bound safetensors, never pickle.

```bash
make sync
make check
make build
```

The Phase 4 smoke artifact can be reproduced in a clean checkout that also has the
approved ignored Phase 3 candidate and review record:

```bash
make reproduce-smoke
make phase4-verify
```

The smoke write is non-overwriting. Exact evolving command outcomes belong in
[the implementation status](docs/IMPLEMENTATION_STATUS.md).

The existing Phase 5 artifact is independently verifiable with:

```bash
make phase5-verify
```

The preserved Phase 6 correction graph is independently verifiable with:

```bash
.venv/bin/python scripts/phase6_rescore_v0_1_1.py verify \
  --config configs/experiments/phase6-main-v0.1.0.toml
```

The checksum-bound v0.2–v0.4 remediation engineering has a separate user-operated
development runner. Dry-run it before starting any long work, and use the status,
stop, and resume wrappers rather than editing run evidence:

```bash
./scripts/run_phase6_pipeline.sh --dry-run
./scripts/run_phase6_pipeline.sh
./scripts/check_phase6_status.sh
./scripts/stop_phase6_pipeline.sh
./scripts/resume_phase6_pipeline.sh
```

Targeted-03's completed training/evaluation evidence has a one-time,
non-overwriting gate certification path that does not retrain:

```bash
./scripts/replay_phase6_targeted03_gate.sh
```

The command exits `9` when the reconstructed unchanged gate is a scientific block.
It writes only under
`runs/phase6-remediation-v0.4.0-targeted-03-gate-replay-01/` and never edits the
preserved targeted-03 source run.

On macOS, the same fixed workflow is available through a small local-only progress
window:

```bash
./scripts/open_phase6_progress_gui.sh
```

The window is an owner testing utility, not the Phase 7 public interface. Opening or
closing it does not start or kill training; Start, cooperative safe stop, and Resume
remain confirmation-gated and preserve existing run evidence. The current default is
`phase6-remediation-v0.4.0-targeted-05`; do not resume or modify any preserved
failed attempt. Its three separate bars show the entire 16-stage rerun, progress within
the current version, and exact current-task work when the runner reports it. The
entire-rerun bar is stage-based rather than a wall-clock estimate. Keep the monitor
open while the pipeline runs: when a verified run first enters `Failed` or `Blocked`,
the monitor requests macOS attention and loops the system `Sosumi` alert at application
volume 1.0 for 45 seconds, with a 23-beep fallback if the sound file is unavailable.
It alerts only once per monitor session, so routine status refreshes do not repeat the
sound. While it is active, the enabled **Stop alarm** button stops the loop and cancels
pending fallback beeps without changing run state. The alarm cannot override muted or
low system volume or an incorrect output device; verify those macOS settings before
leaving a run unattended.

Infrastructure availability is not a positive model result. The routine pipeline
cannot open the frozen final evaluation, and the historical G01–G15 packet is
prohibited as the fresh v0.4 golden gate. The separate fresh final-evaluation executor
is intentionally unimplemented and locked in this release; readiness-looking files
cannot authorize access. Exact self-run, status, stop/resume, review, and safety
instructions are in
[the Phase 6 remediation local runbook](docs/model/PHASE6_REMEDIATION_RUNBOOK.md).
