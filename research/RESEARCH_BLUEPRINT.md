# ReactorBench-LM research blueprint

## 1. Executive framing

### Final project title

**ReactorBench-LM: Training a Small Transformer from Scratch on Synthetic Nuclear-Plant Event Sequences**

`ReactorBench-LM` is the final project name. The “Bench” framing communicates that
the work is a controlled AI experiment with measurable results, not a claim to
operate or advise a real nuclear facility.

### One-sentence pitch

Build and evaluate a small decoder-only Transformer, initialized and trained from scratch, on event narratives generated by a fictional civilian nuclear-plant abstraction with exact simulator ground truth.

### Portfolio pitch

The project combines three strengths visible in Zachary Ryan's background: disciplined operations thinking, full-stack Python application development, and existing AI evaluation research. It creates a genuine move beyond cybersecurity because the centerpiece is the learned model, its data, its experimental design, and its measured generalization.

### Primary research question

How well can a small causal Transformer learn event-sequence language and generalize from individual synthetic fault patterns to unseen combinations of faults and system variants?

### Secondary questions

1. How do model size and training-token count affect in-distribution and compositional performance?
2. Does requiring structured intermediate evidence improve final fault and next-action accuracy?
3. How large is the performance gap between random trajectory splits and leakage-resistant compositional splits?
4. Can the model learn when evidence is insufficient and produce an abstention label instead of inventing a diagnosis?

## 2. Intended contribution

The strongest deliverable is the combination of:

1. A reproducible fictional event-world generator with exact ground truth.
2. A documented synthetic text dataset with strict provenance and non-leaking splits.
3. A decoder-only Transformer implemented and trained from random initialization.
4. Transparent baselines and a pre-registered evaluation matrix.
5. A polished demonstration that visualizes results without presenting outputs as real advice.

The claim should be narrow:

> “This study measures how small causal Transformers learn and generalize over a controlled synthetic event domain.”

It should not claim genuine reactor understanding, real-world fault diagnosis, operational readiness, or safety assurance.

## 3. Fictional system abstraction

### World definition

Use an invented civilian, pressurized-water-inspired energy facility. It may use familiar high-level concepts documented in public education material, but it must not reproduce a real plant design.

Recommended fictional subsystems:

- `HEAT`: abstract heat-source state and heat balance.
- `PRIMARY`: a closed heat-transfer loop with two invented pump trains.
- `TRANSFER`: an abstract heat exchanger connecting primary and secondary sides.
- `SECONDARY`: a steam and feed loop.
- `REJECTION`: condenser and external heat-rejection loop.
- `ELECTRICAL`: generator, two abstract buses, and support-power availability.
- `INSTRUMENT`: redundant synthetic measurement channels and status flags.

Recommended state representation:

- Continuous values normalized to `[0, 1]`, standardized scores, or explicitly labeled `synthetic units`.
- Discrete status values such as `normal`, `watch`, `abnormal`, `unavailable`, `recovering`, and `unknown`.
- No real setpoints, capacities, time constants, material inventories, pressure values, temperatures, or emergency classifications.

### Scenario families

Start with 11 single-fault families and later construct 8–12 two-fault combinations:

1. Sensor drift.
2. Sensor stuck value.
3. Sensor noise burst.
4. Pump efficiency degradation.
5. Pump synthetic trip.
6. Valve lag.
7. Valve stuck state.
8. Heat-transfer efficiency loss.
9. Secondary-flow imbalance.
10. Electrical support interruption.
11. Abstract inventory-loss condition.

`LOAD_TRANSIENT` is a separate benign scenario driver, not a fault family. Its
resolved diagnostic status is `NO_FAULT`, which is also not a fault label, and its
fault-label set is empty.

Compound scenarios should combine fault families whose effects interact in the invented state graph. They must not reproduce a historical event sequence.

### Fictional action-label set

Outputs should be high-level labels rather than real procedures:

- `VERIFY_REDUNDANT_CHANNEL`
- `COMPARE_RELATED_TRENDS`
- `FLAG_SENSOR_SUSPECT`
- `REQUEST_COMPONENT_INSPECTION`
- `SELECT_SYNTHETIC_STANDBY_TRAIN`
- `REDUCE_SIMULATED_LOAD`
- `ENTER_SIMULATED_STABLE_STATE`
- `CONTINUE_MONITORING`
- `INSUFFICIENT_EVIDENCE`

The app and documentation must call these *simulation labels*, not operator instructions.

## 4. Model objective and architecture

### Core model

A decoder-only causal Transformer trained using next-token prediction. The model begins with random weights and learns only from the project corpus.

Core components to implement later:

- token and positional embeddings;
- pre-normalization Transformer blocks;
- masked multi-head self-attention;
- feed-forward network;
- residual connections and dropout;
- tied or untied language-model output head;
- cross-entropy causal-language-model loss;
- autoregressive decoding with greedy, temperature, and top-k modes.

### Tokenizer

Recommended main path: train a project-specific SentencePiece BPE tokenizer with a vocabulary of about 2,000–4,000 tokens. SentencePiece is an Apache-2.0 implementation of standard subword tokenization; the tokenizer model would still be trained exclusively on this project's corpus.

Optional depth extension: implement a small byte-level BPE trainer after the main model works and compare it with SentencePiece. Do not make tokenizer reimplementation a prerequisite for the first experiment.

### Proposed model tiers

| Tier | Layers | Width | Heads | Context | Approximate parameters | Purpose |
|---|---:|---:|---:|---:|---:|---|
| Smoke | 2 | 128 | 4 | 128 | under 1M | Verify loss, masking, checkpointing, and generation |
| Pilot | 6 | 256 | 8 | 256–512 | about 5–7M | Establish learnability and data quality |
| Main | 8 | 384 | 8 | 512 | about 15M | Primary reported model |
| Stretch | 10 | 512 | 8 | 512–1024 | about 30–35M | Only after compute and value are demonstrated |

Parameter counts are estimates and must be calculated from the implemented configuration before reporting.

### Training stages

1. **Smoke training:** overfit a tiny shard to prove the architecture and targets are wired correctly.
2. **Domain pretraining:** causal next-token training on synthetic event logs, incident narratives, and fictional policy cards.
3. **Task adaptation:** continue training the same model on structured prompt/target examples for evidence, classification, summary, and next-action labels.
4. **Evaluation-only checkpoint selection:** select using validation criteria fixed before reading test results.

No hosted LLM should generate the corpus, label data, judge primary metrics, or supply model weights. Human-written grammar templates and deterministic renderers keep provenance clear.

## 5. Evaluation design

### Baselines

- Unigram and trigram language models for held-out token prediction.
- Majority-class predictors for fault and action labels.
- A simple Markov next-event predictor over event types.
- The generator's rule engine as an oracle upper bound, clearly labeled non-learned.
- Optional later baseline: a small LSTM trained on the same tokens and splits.

### Primary metrics

| Task | Primary metrics | Important caveat |
|---|---|---|
| Language modeling | validation loss and perplexity | Compare only with the same tokenizer and split |
| Next event | top-1/top-3 event accuracy, macro F1 | Score structured event labels, not just prose overlap |
| Fault family | exact match, macro F1, confusion matrix | Include single and compound labels separately |
| Evidence | slot-level precision, recall, F1 | Evidence must exist in the supplied narrative |
| Next action | exact match, macro F1, valid-label rate | Labels are fictional simulation actions |
| Summary | fact-slot precision/recall/F1, contradiction rate | ROUGE may be supplementary, not decisive |
| Abstention | precision/recall for `INSUFFICIENT_EVIDENCE` | Test deliberately ambiguous and corrupted cases |
| Calibration | Brier score or expected calibration error | Requires a defined probability extraction method |

### Generalization splits

1. **IID holdout:** unseen seeds from known scenario families.
2. **Template holdout:** narrative template families absent from training.
3. **Component holdout:** invented component identifiers and aliases absent from training.
4. **Severity holdout:** one synthetic severity band absent from training.
5. **Compositional holdout:** specific two-fault combinations never appear in training although each individual fault does.
6. **Counterfactual holdout:** matched cases where one observation changes the correct label.
7. **Noise stress test:** missing lines, reordered non-causal notes, duplicated entries, and irrelevant benign events.

Splits must be assigned at the structured scenario-definition level before any language templates are rendered. Randomly splitting rendered examples would leak rules and wording.

### Experiment matrix

| Experiment | Changed variable | Main finding sought |
|---|---|---|
| E0 | Baselines only | Minimum performance to beat |
| E1 | Smoke, pilot, main size | Model-size effect |
| E2 | 2M, 10M, 25M+ training tokens | Data-scale effect |
| E3 | Direct answer vs evidence-then-answer format | Effect of explicit intermediate evidence |
| E4 | With vs without fictional policy-card context | Context-conditioning effect |
| E5 | IID vs compositional split | Generalization gap |
| E6 | Clean vs noisy observations | Robustness and abstention |
| E7 | SentencePiece vs optional custom BPE | Tokenizer tradeoff |

Report unsuccessful experiments and variance across at least three seeds for the final selected comparison when compute permits.

## 6. Pre-registered success criteria

These are project gates, not claims of real-world safety:

- Dataset provenance coverage: 100% of examples trace to generator version, seed, scenario definition, and renderer/template family.
- Label consistency: 100% of released examples pass generator invariants and target recomputation.
- Split leakage: zero shared scenario IDs and zero prohibited template-family overlap across strict splits.
- Prohibited-source scan: zero real plant names, real procedure identifiers, Navy terms, copied event-report passages, or real setpoint/unit patterns in released data.
- Structured output validity: at least 98% parseable outputs on the main in-distribution test after task adaptation.
- Learned value: the main model must materially outperform the declared non-neural baselines on next-event, fault-family, and action-label metrics; report confidence intervals rather than claiming success from a single point estimate.
- Generalization honesty: report the full IID-to-compositional performance gap even if it is large.
- Application gate: do not build the public-facing demo until the model and dataset pass reproducibility, leakage, and provenance checks.

Exact numerical accuracy thresholds should be locked only after the pilot establishes task difficulty; otherwise they would be arbitrary.

## 7. Compute and tooling plan

### Available local hardware

Apple M3 MacBook Air, 8 CPU cores, 16 GB unified memory. Do not record hardware serial numbers or other device identifiers in project artifacts.

### Local feasibility

PyTorch's MPS backend supports GPU-accelerated tensor and model execution on Apple silicon. The machine is suitable for dataset work, smoke tests, and pilot-to-main small-model training. A fanless MacBook Air can throttle on sustained training, so runtime must be measured rather than promised.

Recommended compute sequence:

1. Run a 500–1,000-step microbenchmark with the pilot configuration.
2. Record tokens per second, peak memory, temperature/throttling symptoms, and checkpoint size.
3. Project full-run duration from measured throughput.
4. Lock the main model and corpus size only after that measurement.
5. Use a rented/cloud GPU only if the main experiment would be impractical locally; keep cloud use reproducible and cost-capped.

### Likely software dependencies

- Python 3.12-compatible environment.
- PyTorch with MPS support.
- SentencePiece for the recommended tokenizer path.
- Standard scientific utilities for metrics and plotting; using these does not replace building the model.
- Parquet support for structured traces and JSONL for text/task examples.

Foundation dependency versions are pinned in the present local `uv.lock`. Later
dependency groups must be pinned when introduced. Until local Git is initialized,
the lockfile's presence is a local integration checkpoint, not a commit claim.

## 8. Safety, information, and portfolio boundaries

### Training-data prohibitions

Do not use:

- real NRC event-notification text, licensee event reports, operator logs, inspection reports, operator examinations, or emergency procedures;
- real facility names, unit numbers, equipment identifiers, operating thresholds, setpoints, capacities, timelines, or response steps;
- Navy service knowledge, naval nuclear propulsion information, recollections, notes, qualification materials, diagrams, procedures, or terminology derived from non-public experience;
- classified, controlled, proprietary, access-restricted, export-controlled, or third-party licensed materials;
- IAEA simulator software or documentation governed by its restricted distribution terms;
- real user-submitted plant data in the eventual interface.

DOE notes that some unclassified nuclear design and security information may still be controlled. The conservative project rule is simpler: only use project-authored fictional operational content.

### Required visible disclaimer

> All systems, events, values, policies, and narratives in ReactorBench-LM are synthetic and fictional. No real plant records, operating procedures, event reports, Navy material, restricted information, or proprietary manuals were used. The model is an educational language-model experiment and is not suitable for operational, engineering, licensing, emergency, maintenance, security, or safety decisions.

### Interface limitation

The eventual demo should expose a scenario selector and generated narrative, not an unrestricted “ask about a nuclear plant” chat box. If free text is later added, it must be constrained to the fictional world and refuse real-facility instructions.

### Documentation

Release a dataset card, model card, experiment card/results report, data provenance manifest, and limitations section. NIST's AI RMF emphasizes documented test sets, metrics, uncertainty, benchmarks, and generalizability limits; the model-card and datasheet literature provides practical formats.

## 9. Research landscape and differentiation

- Transformer architecture: Vaswani et al. introduced attention-based Transformer models in 2017.
- Small-model precedent: TinyStories showed that sub-10M-parameter language models can learn coherent behavior in a deliberately simplified synthetic language domain. ReactorBench-LM uses deterministic project-authored data rather than frontier-model-generated stories.
- Nuclear AI precedent: nuclear fault diagnosis using simulator-generated scenarios dates back decades. More recent INL research applies NLP and generative methods to real operator logs. ReactorBench-LM differs by training a causal Transformer from scratch on a fully controlled fictional corpus and measuring compositional generalization rather than claiming deployment relevance.
- Synthetic compositional studies show that autoregressive Transformers can learn synthetic compositions but remain sensitive to dataset structure and ordering bias. This motivates the strict holdouts and ablations.

The novelty is not inventing Transformers. It is the controlled dataset, from-scratch implementation, evaluation discipline, and personal yet safely abstracted domain choice.

## 10. Canonical implementation phases

The earlier research-only roadmap numbered repository/contracts as Phase 0 and the
minimal synthetic world as Phase 1. That map is superseded. The canonical phase map
used by implementation and security gates is:

### Phase 0 — Workspace and decision audit *(complete)*

- Verify the corrected project path, document source and safety boundaries, and
  resolve decisions that are safe before implementation.
- Preserve dated environment facts without treating the audit as implementation.

### Phase 1 — Repository and contract foundation *(locally integrated)*

- Establish packaging, locked dependencies, strict configuration, developmental
  schemas, deterministic snapshots, documentation, and focused tests.
- Keep local Git initialization separate from integration; do not push or deploy.

### Phase 2 — Structured generator

- Implement stable operation, bounded deterministic transitions, observation
  separation, initial fault families, invariants, and property tests.
- Produce structured development trajectories only after the Phase 1 gate is
  recorded.

### Phase 3 — Dataset and renderer

- Add split-first manifests, deterministic project-authored rendering, provenance,
  prohibited-content scanning, duplicate/leakage checks, and a tiny pilot dataset.
- Expand scenario coverage without using real records or hosted-LLM corpus text.

### Phase 4 — Model correctness

- Implement the project tokenizer and decoder-only Transformer.
- Overfit a tiny shard and validate causal masking, next-token targets, and
  checkpoint save/reload behavior.

### Phase 5 — Baselines and pilot

- Run preregistered baselines and the pilot model on fixed development splits.
- Measure local throughput, memory, and learning behavior before freezing main
  scale choices.

### Phase 6 — Main experiments

- Freeze versioned data and experiment gates; run the main model, registered
  ablations, robustness/OOD evaluation, calibration, and failure analysis.

### Phase 7 — Inference and UI

- Build the narrow scenario browser and controlled model-inference experience from
  recorded artifacts only.
- Display ground truth, model answers, evidence, versions, and known failures while
  keeping the safety disclaimer visible and preventing real-world input framing.

### Phase 8 — Release readiness

- Produce plots, cards, checksums, provenance, SBOM, limitations, and
  reproducibility evidence locally.
- Complete the release allowlist and verification package without pushing,
  publishing, or deploying anything. Those actions remain owner-managed and
  outside this implementation roadmap.

## 12. Research limitations

- This dossier is a conservative design assessment, not legal advice or nuclear-engineering validation.
- No real dataset or simulator was downloaded because the adopted corpus strategy is wholly synthetic.
- Parameter counts, training duration, and model quality remain estimates until code and microbenchmarks exist.
- The fictional world will be internally consistent, not physically predictive.
- A small model may learn templates rather than robust causal structure; the split design and counterfactual tests are meant to expose that possibility, not guarantee against it.
