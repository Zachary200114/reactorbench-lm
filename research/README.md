## Recommended project

**ReactorBench-LM: Training a Small Transformer from Scratch on Synthetic Nuclear-Plant Event Sequences**

ReactorBench-LM will be a small decoder-only Transformer trained from random initialization on a wholly project-authored dataset representing a fictional civilian, pressurized-water-inspired energy facility. The model will learn causal language modeling and several structured tasks over synthetic event narratives: next-event prediction, fault-family identification, evidence extraction, incident summarization, and selection of a fictional diagnostic label.

The research question is:

> How well can a small causal Transformer trained from scratch learn system-event language and generalize to unseen combinations of faults in a controlled, simulator-grounded synthetic domain?

The project is a model-development and evaluation experiment. It is **not** a real plant simulator, digital twin, operator assistant, safety system, emergency tool, or source of engineering guidance.

## Settled boundaries

- The model will be trained from scratch; no pretrained weights and no hosted LLM API will perform the core modeling work.
- PyTorch may provide tensor operations, automatic differentiation, and Apple GPU acceleration. Using PyTorch does not make the model prebuilt.
- All training and evaluation narratives, plant identifiers, state variables, fault rules, thresholds, policies, and outputs will be generated by this project.
- No real event notifications, operator logs, procedures, plant manuals, setpoints, facility names, security details, or Navy nuclear information will enter the corpus.
- Public NRC, DOE, IAEA, ORNL, INL, NIST, and research sources are references for broad concepts, terminology review, governance, and experiment design—not text to scrape into the model.
- Telemetry will use normalized values or explicitly fictional synthetic units rather than real operating units and limits.
- The eventual interface will accept only generated scenarios from the fictional world. It will not solicit or analyze real-facility data.

## Key conclusion from source research

The main dataset should not be “collected” from real nuclear records. It should be **designed and generated** from the versioned Aster Station state machine so every label has known ground truth. This creates a cleaner research contribution, avoids training-data ambiguity, enables rigorous compositional holdouts, and prevents the model from masquerading as a real operational tool. The accompanying golden suite fixes the behaviors that later implementation must demonstrate, including false-positive resistance and required abstention.

## Hardware assumption

The current computer is an Apple M3 MacBook Air with 16 GB unified memory. PyTorch officially supports GPU-accelerated training on Apple silicon through its MPS backend. The recommended progression is approximately 5–7M parameters for the pilot, approximately 15M for the main model, and approximately 30M only as a stretch after local benchmarks.
